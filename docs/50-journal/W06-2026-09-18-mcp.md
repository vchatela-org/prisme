# W06 · 2026-09-18 · The MCP server, and the confirmation that can actually go stale

**Agent:** Claude Opus 5 · **Duration:** one session · **PR** #26 · **Outcome:** complete

## What was done

Seventeen tools on one stateless Streamable HTTP endpoint, mounted on the API process: eight that
read, nine that write, every one of the second kind a dry run until a confirmation bound to its diff
comes back. The tool kit mirrors `http/route.ts` deliberately — a tool is data before it is
behaviour, so the dispatcher, the manifest and the contract test are generated from one object and
cannot disagree about which scope a tool needs.

Nothing here decides anything. Every handler delegates to the service layer W05 built for exactly
this reason, and the only logic in the tree is the projection from a service's answer down to
something small enough for an agent to read.

## Decisions taken

### The SDK was not taken, and that is ADR-0024

The reference SDK is the obvious choice and normally the right one. Two things made this case
different, and both are evidence rather than preference.

Its seventeen runtime dependencies include Express 5, `cors`, `express-rate-limit`, an OAuth client,
an SSE client, a second schema validator and a process spawner. `apps/api` is a Hono process, and
adding a second HTTP framework and an OAuth client to the tier the threat model calls *the sharpest
edge in the system* is a real cost for a transport we mount on a route Hono already serves.

The layers the SDK is actually worth having for — sessions, authorization, rate limiting, schema
conversion — are the four prisme has already decided. Wiring it in would have meant bridging its
transport to Hono's `Context`, which `@hono/node-server` exposes only outside the Fetch API — the
one path every test in `apps/api` drives the application through. The surface with the highest
consequence of being wrong would have become the one hardest to test.

**The cost is stated in the ADR rather than discovered later: conformance is ours.** `protocol.test.ts`
pins the shapes the revision requires, in place of the SDK's types going red on a changed
specification.

### The endpoint reads the tool's scope *before* it authenticates

This looks backwards and is the whole reason the kill switch works. `authorize()` takes the required
scope as an argument and compares it against what the write switch withholds — so the endpoint
parses the JSON-RPC envelope, finds which tool is named, and hands *that tool's* scope to the
authorizer. Engaging the switch makes a write tool unreachable with nothing written here to notice.

`auth/write-switch.ts` predicted this in as many words: *"every MCP write tool W06 adds is a new
place the check has to be repeated, and the one that gets missed is discovered during the incident
the switch exists for."* Authorizing the endpoint once with some fixed scope would have been simpler
and would have thrown that away.

The consequence is that untrusted JSON is parsed before the caller is known. It is bounded — a size
cap, then Zod, then nothing else touches it — and it is load-bearing rather than sloppy.

### `tools/list` is filtered to the scopes held

Not in the brief. A manifest that lists tools the caller may not invoke is a map of things to
attempt, and an agent will spend turns attempting them. A read-only credential now sees eight tools
and no write tool exists as far as it is concerned.

### Both reconciler tools require `write:sync`

`plan_preview` changes nothing, inward or outward, and a finer `read:sync` would have let a
read-only agent look without touching. It was not taken: `POST /sync` requires `write:sync` for
`mode: plan` too, and running a pass does reach the external tools. Diverging from a scope W05 had
already assigned is a decision, and this workstream had no mandate to make it. Named in
`tools.contract.test.ts` as the one read tool behind a write scope, so a second one cannot appear
quietly.

## Surprises

### A plan that cannot go stale is not a control

The mechanism is only as good as the diff it hashes, and two ways of writing a diff quietly destroy
it — opposite ways, which is what makes them easy to get both wrong in one file.

**A diff that reports only what it wants.** A `create` describes a row that does not exist. It
hashes identically whatever the world does, so the confirmation can never go stale and the second
call is authorised no matter what happened in between. `capture` now reads the initiatives already
carrying that title in that area *into the diff*, so a duplicate appearing between the dry run and
the execution moves the hash and the confirmation is refused. `start_review` does the same with the
sessions already open.

**A diff that depends on the clock.** The opposite failure, and worse, because it looks like the
control working. Anything time-varying inside a plan makes every confirmation stale within a
millisecond, "the plan has changed since it was shown" becomes the ordinary outcome, and whoever
sees it learns to retry until it works — which is precisely what `hashPlan`'s own comment warns
about. `apply` is where this bites: a reconciler result carries `startedAt` and `finishedAt`, and
both are dropped before the diff is built. There is a test whose only job is to plan and immediately
execute, which is the cheapest possible guard against a clock creeping back in.

### `creates` was counting a thing that creates nothing

The state probe added to `capture` was written as `op: 'create'` — it sits in the changes list, and
`create` was the nearest op. The integration test caught it immediately: `plan.creates` read 2 for a
plan that creates one initiative.

That is not cosmetic. `creates` is the number ADR-0010 guard 3 is about, and it is the number a
human reads at the moment of deciding whether something is about to duplicate their backlog.
Inflating it teaches whoever reads it that the count is approximate, and a count known to be
approximate is one nobody checks. There is now an `observe` op for state a plan reads only so that
its hash can move, and `countCreates` ignores it.

### A dry run that cannot show the refusal is not a preview

Promoting a principle, dropping without a reason, closing a review twice: each was originally
refused by the service at execution time, which meant the dry run would have shown a confident diff
and the confirmed call would have failed. Every one of those checks moved into `plan`.

For `promote_takeaway` that needed something the service layer did not expose — there was no way to
read one takeaway by id. A four-line, read-only `getTakeaway` was added to `LaneService`, outside
this workstream's declared tree and flagged as such in the pull request. The alternative was a dry
run that could not see the refusal, which is the control being decorative.

### The privacy scan caught the generated manifest, and the local scan had not

The first commit was refused by the pre-commit hook. `z.uuid()` renders as `format: "uuid"` **and** a
regex that spells out the nil and max UUIDs as literal alternatives — two literal UUIDs per uuid
field, across seventeen tools. A workspace id is a UUID, which is exactly why that pattern is on the
deny-list. The `pattern` is now dropped where `format` says the same thing.

The part worth recording is that `./scripts/privacy-scan.sh` had reported clean minutes earlier.
Worktree mode iterates `git ls-files`, so **a workstream's new files are invisible to it until they
are staged**. The pre-commit hook caught it and nothing reached a push — but "run the local
equivalent before you push" is currently a weaker promise than it reads, and the gap is widest for
exactly the situation a workstream is in.

### The event log cannot name who did it

The brief asks for every MCP write to land in the event log "with the token identity as actor".
`event_log.actor` is `text NOT NULL CHECK (actor IN ('human','agent','sync'))` — it records the
*kind*, and widening it is a migration in a tree this workstream does not own.

What is delivered is the definition-of-done wording — the correct actor — plus a durable row that
does name the subject. Every MCP write consumes a `confirmation_token` row carrying `operation`,
`subject` and the diff hash, and since no write tool can execute without one, the identity behind
every MCP write is recoverable by construction. An `actor_subject` column is the honest fix and is
listed as a follow-up rather than smuggled in.

### What a cold agent made of the descriptions

The brief asks for the tool descriptions to be reviewed by running a real agent against them rather
than by reading them back. That was done: a fresh agent, given nothing but the generated manifest —
no repository, no context — was asked which tool it would call first for twelve ordinary requests,
and then what it found ambiguous.

It was worth doing. The descriptions read well and the agent still could not complete four of the
twelve, for one reason repeated four times: **every write tool names an initiative by id, and
nothing said how to get one.** `list_initiatives` has a `search` argument that plays exactly that
role, and no description mentioned it, so the agent inferred the sequence correctly but with medium
confidence each time and said so. Three further findings were real:

- **`plan_preview` and `apply` were indistinguishable.** Both write nothing on the first call, both
  return a plan, and neither said why two tools exist. The agent flagged it as the single worst
  ambiguity and predicted it would call both redundantly.
- **`list_takeaways` looked capable of something it cannot do.** prisme holds the link and not the
  text, so a takeaway cannot be found by topic — the description said so, in its last sentence,
  after the agent had already committed to a plan that needed it.
- **`objectives` has no quarter**, and "how are my Q1 objectives" is an ordinary question with no
  documented answer.

Smaller: `promote_takeaway` never said where the new initiative lands, `capture` gave no guidance for
choosing an area from an utterance that names none, and nothing warned that a bad `capture` has no
undo.

All of these were fixed and a second cold agent run against the revised manifest. The four requests
that had been medium or low confidence came back high, with the fixed sentences quoted back as the
thing that decided them — and the `plan_preview`/`apply` pair went from "worst ambiguity" to "I would
never call both".

**Three of the second run's complaints were artefacts of how the descriptions were handed over, not
of the descriptions.** The harness extracted names, prose and argument *names* — so the agent never
saw the `to` enum, the `confirmationToken` argument's own description, the `_meta` scope, or the
`instructions` returned by `initialize`, all of which a real client receives. It then reported, quite
reasonably, that the statuses were undocumented, that the two-call confirmation pattern had to be
inferred by analogy, and that scopes were documented inconsistently. The lesson is about the method:
**a review harness that shows an agent less than a client gets will manufacture findings**, and the
temptation is to "fix" them by inflating the prose. Two were left alone. The third — the status
ladder — was worth one sentence anyway, because knowing that `done` exists is not the same as
knowing which rung means finished.
