## What was done

[The W00 entry](W00-2026-09-15-foundations.md) ends at the pull request. This one closes the four

**The Harbor configuration is complete.** The registry host and project are repository variables and
the robot account's username and password are secrets; the publish job, which until now skipped by
design (`if: vars.HARBOR_REGISTRY != ''`), is armed from this point. Nothing about those values is
written down here — a registry host is infrastructure detail and belongs to the deployment
repository ([`17-privacy.md`](../17-privacy.md)).

**`v0.0.1` was pushed, and `publish.yml` ran for the first time — into the bug it was hiding.** Both
matrix jobs failed before building anything: the runner is itself a pod in the cluster, with no
`/var/run/docker.sock`, so `docker/setup-buildx-action` had no daemon to reach and died on
`connect: no such file or directory`. The fix is the driver the organisation's shared Harbor workflow
already defaults to for exactly this reason — `kubernetes`, which runs BuildKit as pods in the
cluster instead of a local daemon. A sibling repository publishing from this same runner set is the
proof it works. `images.yml` keeps the default driver: it runs on a hosted runner, which has a
daemon.

**`CI_RUNNER` is left unset, deliberately.** The workflow falls back to `arc-runner-set`, which is
the organisation's runner scale set and serves every repository in the org, so a value would be
copied from the deployment repository into one that does not need to know it. The first tag proved
the default resolves to a real runner — the job started and failed *on* it, which is a different
outcome from never starting. Worth knowing what the default costs: if the scale set is ever renamed,
a publish job does not fail, it queues forever — a hang rather than a red check, which is the
quietest way a runner misconfiguration can present.

**A repository variable with no reader was removed.** The image-name variable had been set beside the
two the workflow actually reads, and it is clear where it came from: the org's shared Harbor workflow
takes a `harbor_image` input, sibling repositories pass it from a variable of that name, and this one
was set by the same hand — but prisme publishes directly and derives its image names from its own
matrix. Nothing consulted it. GitHub does not report an unused variable, no workflow fails, and no
file in the repository mentions it — a configuration surface that looks meaningful, costs an hour the
first time somebody reasons about it, and is invisible to every gate we have. If prisme ever moves
back to the shared workflow, the variable comes back with it.

**One comment had survived the correction it belonged to.** `images.yml` still described publishing
as going "through the shared Harbor workflow", which the same PR had corrected in
[`15-runtime.md` §1](../15-runtime.md) and in `publish.yml`'s own header. A fact corrected in two
places and left in a third is how it un-corrects itself.

**The merged branches are gone** — `ws/W00` and `docs/branch-and-pr-protocol` on the remote, and the
two pre-rewrite Dependabot refs pruned locally.

`STATUS.md` now carries W00 as 🟢 against #5, and wave 1 as: W00 landed, W01 · W03 · W07 cleared to

## Decisions taken

**The publish path was exercised rather than left as an untested claim.** Every other gate here was
*watched fail* before it was trusted — that is the standard W00 set for itself, and publish did not
meet it. Exercising it means pushing an image nothing consumes, under a tag chosen to be disposable:
a deliberate act with a real side effect rather than a check, so it belonged to the human, and the
human authorised it. That decision is what found the missing daemon. Had it been deferred, the bug
would have waited for the first real release, where it would have cost a release instead of a probe.

**The fix is a driver, not a runner.** Two ways to build an image on a runner with no Docker socket:
give the runner a socket — a daemon sidecar, or the host's mounted into it — or stop needing one. The
first changes every job on that runner set, including jobs in repositories with nothing to do with
prisme, and hands a container-building capability to all of them. The second is one step in one
workflow, and it is also the already-decided answer: the shared Harbor workflow defaults to it, and
the namespace it needs exists for this purpose. The repository asked for the narrower change.

**The first tag is `v0.0.1`, and it is a probe, not a release.** `github.ref_name` becomes the image
tag, so this named the first images — worth choosing rather than discovering. `v0.0.1` says what the
thing is: a skeleton. The API answers `/healthz` and `/readyz`, the sync entrypoint still logs that no
reconciler is registered, and no domain table exists. The first tag that *means* something will be cut
when there is something to run.

## Surprises

**Every item left over was invisible to every gate.** All four close-out items are the same shape: a
variable with no reader, a runner label inherited from a default, a comment in a file no test parses,
and branches already merged. Sixteen checks were green over a repository that still had four small
wrong things in it. That is not a defect in the checks — none of these is checkable by executing the
repository — but it is worth knowing before green is read as complete: **the gates cover what the
code does, and nothing covers what the configuration says.** A configuration mistake is silent by
construction, which is the same failure mode as a gate nobody has seen fail, arriving through the
door nobody watches.

**The publish workflow was valid, green, and could not run.** Nothing in CI could have caught the
missing Docker socket. `images.yml` builds the same two Dockerfiles successfully, from the same
commit, on a hosted runner — the failure lives only at the intersection of *this* runner and *this*
driver, and no check runs publish's steps anywhere. The workflow parsed, the YAML was right, every
action was pinned, and the runner did answer. It was still broken, and it took a real run to say so.
This is the W00 lesson arriving from the other direction: a gate nobody has seen fail teaches
nothing, and neither does a workflow nobody has seen run.

**Dependabot opened nine pull requests within two minutes of the merge**, and the two that fail say
something about the others. The Node 24 → 26 bumps in both Dockerfiles fail on `corepack: not found`
— Node 26's image no longer ships it — where [`15-runtime.md` §1](../15-runtime.md) records the
`trixie-slim` builder as built. They are not mergeable as they stand; they are a base-image migration
with a Dockerfile change attached, and they need that decision rather than a merge. The Next.js major
builds and pushes green, which is a fact about the pins the spec records and not a reason to take it.
The remaining seven are ordinary.
