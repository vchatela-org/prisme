# W14 · 2026-09-18 · Authentication, authorization and the gates that check the gates

**Agent:** Claude Opus 5 · **Duration:** one session · **PR** [#23](https://github.com/vchatela-org/prisme/pull/23) · **Outcome:** complete

## What was done

The mechanism W05 left a hole for. `apps/api/src/http/authorize.ts` built the *shape* of the
authorization question and answered it `no` until something was installed; this installs it.

- **The assertion verifier** — [ADR-0021](../20-decisions/0021-verified-forward-auth-assertion.md)
  as code. `alg` is checked against a fixed asymmetric list on the decoded header *before any key is
  fetched*, then signature, `iss`, `aud`, `exp`/`nbf` with skew, `exp - iat` against a maximum, and
  a `sub` allow-list. Identity is `sub`; username and email are display material.
- **Scoped API tokens** — Argon2id at rest with a pepper that is not in the database, plaintext
  shown once, scoped with no wildcard, expiring, revocable individually and in bulk, `last_used_at`
  recorded, and a `prisme_pat_` prefix a scanner can recognise.
- **The authorizer** — assertion XOR bearer, verify, origin check, rate limit, kill switch, then
  hand back an identity and let the existing `holdsScope` do the rest.
- **Diff-bound confirmations** for W06's write path: short-lived, single-use, burnt on any attempt,
  and rejected when the plan has moved.
- **The kill switch**, which withholds scopes rather than setting a flag.
- **The web tier**: strict CSP with per-request nonces, CSRF origin checks, the secure-header set,
  and the same verifier the API uses.
- **A negative-control job** that plants a generated secret and a generated deny-list hit and fails
  if either scanner accepts them.

## Decisions taken

**The kill switch withholds scopes; it does not set a flag.** The obvious implementation is a
boolean the reconciler consults, and it protects the path somebody remembered to wire it into —
every future write route, every MCP tool W06 adds, every creation flow W15 builds is a new place to
repeat the check, and the one that gets missed is discovered during the incident the switch exists
for. Engaging it instead removes scopes from every principal in the authorizer, so a write route is
unreachable because the caller no longer holds the scope it declares. A tool written next year is
covered on the day it is written.

**It can only ever subtract.** `SYNC_WRITE_ENABLED` stays the outer gate and `GET /settings` stays
read-only, as W05 built it. Releasing the switch returns prisme to what the deployment already
allowed; no API call can grant a write capability the deployment has not. A break-glass that can
also un-break the glass is a privilege escalation with a friendly name.

**Argon2id stays, and the repetition is what was removed.** A password hash is slow on purpose and
a bearer token is presented on every request. The usual escape — "tokens are high-entropy, SHA-256
is fine" — is how a database dump becomes a set of credentials. Instead, a short in-memory cache
holds only the *immutable* half of the answer: whether this exact string matches that row's hash, a
fact that cannot change because a token's secret is never updated. Revocation, expiry and scopes are
read from the database on every single request. A test pins that a revoked token stops working
immediately rather than at the end of a cache window.

**The origin check binds to the assertion path, not to every request.** CSRF is an ambient-credential
attack: a browser attaches the gateway's session cookie to a cross-site request without being asked,
and does not attach an `Authorization` header to anything. Requiring an `Origin` from a script would
cost usability for no security. A *missing* `Origin` on the assertion path is a refusal — every
browser sends it, and "probably not a browser, let it through" is a bypass with a bookmark on it.

**A confirmation returns its record rather than a boolean**, against the brief's literal contract.
"The world moved" and "that token was already used" are different things to put in an audit line,
and a boolean is something a caller can forget to check.

**The verifier is a package, `@prisme/auth`, and it knows nothing about scopes.** ADR-0021 rule 6
wants one implementation on both tiers. The first attempt kept it in `apps/api` and exported
`@prisme/api/auth/verify` for the web tier — one implementation, and still wrong: a `workspace:*`
edge from `@prisme/web` to `@prisme/api` pulls the whole closure (the Postgres driver, Hono,
`@node-rs/argon2`, `@prisme/sync`) into the web image and its build. The `images` check failed on
it, which was the good outcome; the *reason* it should fail is the trust boundary, not the build
error. `apps/web/Dockerfile` already says the web tier holds no database credential, and shipping it
a driver it has no use for widens the blast radius of an XSS for no feature gain.

So the verification primitives moved to `packages/auth`, and `verifyAssertion` now returns a
`VerifiedAssertion` — a subject and display material — rather than a `Principal` with scopes.
Authorization is prisme's domain (docs/14-threat-model.md §3), so exactly one place turns identity
into authority, and it is the place with the scope vocabulary in it. A shared package is not a
workaround for the dependency graph; it is the dependency graph telling the truth about the
boundary.

## Surprises

**Eight things running found that reading did not.**

1. **The confirmation consume had a race that only a real database could show.** A ten-way race
   produced two winners. The self-join used to fetch the pre-update image reads the original
   snapshot, so under `READ COMMITTED` the second transaction blocks on the row lock, re-checks its
   `WHERE`, and *still* sees `consumed_at` NULL on the `FROM` side. The `WHERE` clause is now the
   mutual exclusion, and the "already used" branch runs only when nothing was updated — where it
   races with nothing, because `consumed_at` never returns to NULL.
2. **Next.js loads middleware from `src/` when the app has a `src/` layout.** At the path the brief
   names, `next build` was green and the middleware manifest was empty, so every security header was
   silently absent. A CSP that is not sent is worse than no CSP: the build passes either way.
3. **`config.auth` was assembled only for the API.** With the variables newly required of the web
   tier, it came back `undefined`, the middleware's defensive fallbacks turned that into an empty
   policy, and the process died reporting `AUTH_ALLOWED_SUBJECTS is empty` about a variable that was
   set correctly. The fallbacks went with the fix — a default that stands in for missing
   configuration turns a five-second problem into an afternoon.
4. **Vitest runs test files in parallel**, and two database-backed suites truncating one PostgreSQL
   between tests means one empties the other's tables mid-test. Invisible while W05's suite was the
   only one; a dozen failures in a suite nobody had touched as soon as there were two. The
   integration project now runs its files one at a time.
5. **`new URL` normalises `[::ffff:127.0.0.1]` to `[::ffff:7f00:1]`**, so the SSRF guard was
   checking a spelling it never receives.
6. **The `images` check caught the dependency edge nothing else would have.** Typecheck, lint, test
   and build were all green with `@prisme/web` depending on `@prisme/api`; only building the actual
   container showed that the web image's builder has no `apps/sync` source to compile. The build
   error was the symptom; the trust boundary was the problem. Verified after the fix by building
   both images and reading the web image's bundle back: the verifier is in it, `argon2id`,
   `prisme_pat_` and `confirmation_token` are not.

7. **`images` also caught a boot dependency that should not exist.** The key-set check ran at start-up
   and treated "unreachable" like "unusable", so an API pointed at an identity provider that does not
   answer refused to start — and `/healthz` "has no dependencies" is a requirement
   (docs/15-runtime.md §1). It is the right check with the wrong blast radius: an empty key set never
   fixes itself and is fatal; an unreachable one usually fixes itself in seconds, and refusing to
   start turns a provider blip into a crash-looping API, taking down reads an agent's bearer token
   could have served without the provider at all. The two are separate errors now, the key set
   resolves lazily, and a failure is not cached — so the first request after the provider returns is
   the one that works.

8. **The negative control was itself unreliable — the worst kind of check to ship.** It passed
   locally and failed on its own first CI run, because it was aimed at gitleaks' `generic-api-key`
   rule, which scores Shannon entropy and drops candidates containing stopwords. Whether it fired
   depended on which random string the generator produced that run. A control that is right most of
   the time is not a control; it is noise, and noise gets muted. It plants a private-key block now,
   matched on a fixed header with no entropy threshold, so it fires every time or never.

**And one thing that was checked rather than assumed.** `@node-rs/argon2` is a native addon, and the
API runtime is distroless with no toolchain. It hashes and verifies correctly inside the built
image — worth knowing before a deployment finds out.

**Two checks went red on the first push, and both were right about the code.** CodeQL flagged
`js/incomplete-url-scheme-check` as high on the hostile-content test: it checked `javascript:`, then
`data:`, and a list of the schemes somebody thought of is exactly the shape of check that fails —
`vbscript:` was missing. The sanitiser in `packages/connectors` was never doing that; its
`ALLOWED_URL_SCHEMES` is `{http:, https:}` and everything else is dropped. The weaker assertion was
the *test*, quietly checking less than the code guarantees. And `lint` failed on thirteen
`no-unsafe-*` errors in correctly typed code, which was the first sign of the dependency-edge
problem above.

**Three local gates refused a commit on the way here, and all three were right.** The privacy
deny-list on a `10.x` literal in a test; `gitleaks` on a token-shaped constant; `ggshield` on an
invented `postgres://` URI. In each case the fixture was fixed and the gate left alone — the
offending values are now assembled at run time, with the reason written beside them so nobody
"tidies" them back. That experience is why the negative-control job exists: the gates are real
enough to be annoying, which is the only evidence worth having.

**A discovery URL rooted at the issuer's origin asks a different application.** The issuer carries a
path, and `new URL('/.well-known/…', issuer)` throws that path away. RFC 8414 does specify the
rooted form; the providers this is pointed at serve the appended one.

**Reading the GitHub API found drift in the checklist that reads it.** Three lines of
`docs/17-privacy.md` §4 were stale, including one asserting that admins are excluded from branch
protection when `enforce_admins` is now on.

**One red check was genuinely not ours.** An `images` run failed with
`error writing layer blob: failed to parse error response 401` — the GitHub Actions cache backend
refusing a layer write, on a workflow that pushes nothing. It passed on re-run with no change. Worth
recording because the protocol asks for it explicitly: say so rather than looping silently, and
never reach for the gate.

## Follow-ups

- **`golden fixtures` is not in `main`'s required-check list**, though `STATUS.md` records it as
  required from W01 (#17). A branch-protection change, so it is listed here rather than made
  silently. **Owner: the human merging this.** The same applies to `security gate self-test`, which
  becomes required from this commit.
- **Two secret-scanning settings are still off** — validity checks and non-provider patterns. The
  repository-level API call is refused, matching the P0 finding that they need an organisation-level
  setting. The exact command is in `docs/17-privacy.md` §4. Non-provider patterns is the one that
  matters now: prisme's tokens carry a prefix a scanner could be taught. **Owner: the human.**
- **Next 16 deprecates the `middleware` file convention in favour of `proxy`**, with a codemod. It
  still works and the brief names `middleware.ts`, so it was left alone. **Owner: whoever bumps Next
  past 16.**
- **The rate limiter is per process.** On one replica that is the limiter; on two it is twice as
  generous. A shared one would need Redis, which `docs/15-runtime.md` does not have and ADR-0018
  argues against. Documented as an approximation, not a hole.
- **`deleteExpiredConfirmations` has no caller yet.** Consumed rows are harmless and tiny; whoever
  adds a maintenance pass should call it.
- **W06 consumes the confirmation mechanism** — `createConfirmationService` and `hashPlan` are
  exported and tested; nothing wires them to a tool yet, because the tools are W06's.
- **W14 is not a phase.** Re-check it whenever a workstream adds an endpoint, a tool or a connector.

## Specs touched

- [`docs/15-runtime.md`](../15-runtime.md) §2 — the three `AUTH_*` rows gain a `W`. The P0 draft was
  wrong rather than out of date: ADR-0021 rule 6 has the web tier verifying too, and there is no
  verification without the issuer, the audience and the subject allow-list. `DATABASE_URL` stays
  absent from the web contract, which is the boundary that matters.
- [`docs/17-privacy.md`](../17-privacy.md) §4 — the checklist re-read from the GitHub API, three
  stale lines corrected, and the two settings a human still has to make split out with the command.

No ADR was contradicted, and none was needed: ADR-0021's nine rules were sufficient to build
against, which is what a good ADR feels like from the implementing end.
