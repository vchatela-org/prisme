# W13 · 2026-09-20 · History backfill → capacity actuals

**Agent:** Claude Opus 5 · **Duration:** one session · **PR** #33 · **Outcome:** complete

## What was done

`prisme-sync backfill --from <date>` reads the task tool's completion history as far back as it is
asked to, attributes each completion to an area, estimates its duration, classifies its lane,
reconstructs ritual adherence, and materialises per-area capacity by week.

Everything before this ran on `task_mirror`, which is the *anchor subtree*. Completions outside an
anchor, and everything completed before prisme existed, were invisible — so the balance factor was
computed from whatever fraction of a life happened to be under an anchor in the last four weeks.

- `packages/db/migrations/0006_backfill.sql` — `completion_history`, `capacity_week`,
  `backfill_cursor`
- `apps/sync/src/backfill/` — eleven modules, seven of them pure, plus their tests
- `packages/connectors` — `fetchCompletions` grows an optional `until`; `Completion` carries
  `recordedDuration`

## Decisions taken

**The location is stored; the area is not.** `completion_history` holds the external project and
section, and attribution runs from `area_mapping` on every pass. This is the single decision the
rest of the design hangs off: adding a mapping for a project that has existed for three years
re-attributes three years of history **without fetching a page**. Proved against a live database —
adding one mapping row took a corpus from 68 unattributable completions to zero, with zero windows
fetched. A stored `area_key` would have frozen the first answer into the record.

**Idempotence is the primary key, not bookkeeping.** `(external_task_id, completed_at)` is the
identity of a completion — a recurring task completes many times under one id — so re-running cannot
double-count whatever the caller does. The definition of done calls this the test that matters, and
it is now a property of the schema rather than of the code that writes to it.

**A day-scale duration is not an effort.** W03 deliberately kept the unit rather than flattening to
minutes and left the decision here. A day-scale duration is a block-out in a calendar: converting it
to 1440 minutes would let one all-day task outweigh a fortnight of real work. It falls through the
preference order like an absent duration, and is **counted**, so the fall-through is visible rather
than silent.

**Extending backwards is not a resume.** A cursor saying "everything from X is here" plus a request
starting before X re-fetches the whole range. Resuming at the cursor would advance it over a stretch
nothing had read, and the hole would be permanent — every later run would resume past it too.
Re-fetching costs requests; the primary key means it cannot cost correctness.

**Adherence is measured per period, not per tick.** Daily is seven opportunities in a week, weekly
is one, monthly is one in a month. A daily cadence bucketed daily makes every row a 0 or a 100 and
the chart a barcode. Over-completion is clamped — `adherence_cannot_exceed_opportunity` refuses it
outright — and reported, because a habit whose completions regularly exceed its cadence has the
wrong cadence, and that is worth seeing rather than discarding.

**A ritual with no bound task is absent from the series, not zero.** A row of zeroes reads as "never
done", which is a different and much more damning claim than "not measurable". It is named in the
report instead.

**Capacity accounting follows the area's kind, always.** Lanes *are* areas with a different kind
(docs/10-model.md §3), so Signals contribute no minutes and Run does, exactly as `computeCapacity`
decides it. `lane` is a label on top: a ritual's completions are real time in a real area *and* the
series adherence is reconstructed from. Nothing here excludes a ritual from capacity.

No new ADR. Nothing contradicts an accepted one, and the three new tables own no field of any
external object — `completion_history` is the task tool's data, read-only, and prisme writes back
neither the measurement nor the estimate it derives (that would be OQ-7).

## Surprises

**The materialised weeks and the covered instants are not the same range.** `weeklyCapacity` buckets
by Monday, so a backfill starting on a Sunday produces a row for the Monday *before* the range
begins. `replaceCapacityWeeks` deleted by the covered instants, so that row sat outside the delete
and inside the insert, and **the second run collided on `capacity_week`'s primary key**. Both bounds
now come from `startOfWeek`, so where a week begins is one function's answer rather than two.

The part worth remembering is why no test caught it. The in-memory store had the *identical*
off-by-one, so the unit suite agreed with the SQL and both were wrong — and every fixture in it
started on a Monday, which is exactly the case that cannot fail. Only a real second run found it.
The fake now refuses a duplicate key the way the table does, and the regression test starts on a
Sunday **with a completion in that first partial week**, because without one the row the defect is
about never exists and the test passes either way.

**A new table with a foreign key breaks every truncate list in the repository.** `capacity_week`
references `area`, and PostgreSQL refuses to `truncate` a table that something references unless the
referrer is in the same statement. So omitting it did not strand rows, it made the whole statement
error — **106 tests went red in two suites nobody had touched**. That is the deliberate absence of
`cascade` working exactly as `apps/api/src/test-support/database.ts` says it should: adding a table
to the schema is adding it to those lists. Both are updated.

**The deny-list was right about a literal UUID again.** A synthetic ritual id in a test matched, as
W06's generated manifest did. The fix is not an ignore entry — it is that nothing in the fake needs
a UUID's shape, so it does not have one.

## What was deliberately not done

**The document tool is still not read**, so the declared-duration tier of the preference order is
unavailable on every run today. `processes.ts` is built, unit-tested and unreachable for exactly the
reason W12 recorded: nothing in this repository loads the role bindings, so `createDocToolClient`
has no caller and `processes_db` is not addressable. The report says `document tool   not read —
the declared-duration tier is unavailable` rather than presenting a two-tier estimate as a
three-tier one. **This is the same missing dependency, not a second one.**

**Recurring upkeep that is not a ritual has no reachable process page.** The join is page → ritual →
task through `entity_external_ref`, which is structural and needs no titles — deliberately, because
title matching is what W12's rule 4 showed is hard to get right, and because a real task title is
instance data this application would then be holding in order to compare it. Run-lane work outside a
ritual therefore falls to the configured default, and the report states the resulting share.

**Nothing displays any of this.** `capacity_week` has no reader: W09's dashboard and the balance
factor still compute from `task_mirror` through `store.initiatives.completions`. Wiring the
materialised rows into `/areas` and `/kpi` is an API change and belongs to whoever owns that next —
see the follow-up below. The brief puts display in W09's scope, so this is the boundary working, but
it does mean the backfill's output is not yet visible anywhere but its own report.

**No backfill CronJob.** The command is run by a human, deliberately: it is a one-off migration step
with a required start date, not a scheduled pass.

this workstream's tests is made up. The **report is instance data at runtime** — it prints unmapped
project ids and ritual names — and is marked as such in `report.ts`, `run.ts` and `main.ts`; none of
it has been pasted here. The throwaway harness that drove a 1 568-completion synthetic corpus
against a real database was **built and deleted**, for the sixth time.
