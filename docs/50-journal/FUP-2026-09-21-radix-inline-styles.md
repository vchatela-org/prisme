**Agent:** Claude · **Duration:** one session · **PR** (this branch) · **Outcome:** complete

Closes W07's recorded follow-up: *"Radix's inline styles, above. Owner: W07 with W14. The options are
a `pnpm patch`, replacing the two primitives that carry visible residue, or accepting it; none should
be `'unsafe-hashes'`."* W09, W10, W11 and W15 each confirmed the count and each recorded that it

## What was done

- **Five `pnpm patch`es** moving Radix's offending static `style` attributes onto class names:
  `react-select` (the hidden native `<select>`, and `SelectValue`'s `pointer-events`),
  `react-radio-group` (the hidden radio behind each item), `react-roving-focus` (`outline: none`),
  `react-tabs` (the mount-animation suppression) and `react-toast` (the viewport's
  `pointer-events: none`).
- **The classes those patches name**, generated by `packages/ui`'s token sheet — the other half of
  the same change, and the reason it lives there rather than in `apps/web`'s stylesheet: a class in a
  patch and a rule in the generated sheet are two halves of one thing, and a reader who finds one
  should find the other.
- **Four render cases in `no-inline-style.test.tsx`**, for the components that used to carry the
  violations. They are the mechanism that makes patching a dependency safe here at all.

## Decisions taken

**A patch, not a replacement and not acceptance.** The three options W07 listed, weighed: replacing
the primitives only fixes the two that carry visible residue and leaves Radix's internals — dialog
titles, the toast viewport, roving focus — still firing; accepting leaves a real rendering defect,
because the hidden native controls become *visible* under the policy rather than merely logged.
Patching is the only one that gets to zero.

**The risk of a patch is a red test, not a silent regression — and that is what makes it admissible.**
A patch that stops applying after a dependency bump is the scary failure mode of this approach: the
`style` attributes come back and nothing says so. `no-inline-style.test.tsx` renders the four
components and fails on any `style` attribute, so the failure is a named failing test. It was
**watched fail**: reverting one patch on disk by hand reds the suite with
`Select (Radix) renders a style attribute` and the exact attribute printed.

**Every value in the compat block is copied, not chosen.** The file it lives in has a rule — the
token table is the only source of values — and the rule is kept by copying: `clip: rect(0,0,0,0)`
and the rest come verbatim from the Radix source they replace. Nothing there decides a colour, a
size or a duration.

**`apps/web`'s stylesheet was not touched.** `globals.css` says "three imports and nothing else —
every value below this line would be a design decision made outside the token table", and that is
still true.

## Surprises

**One of the five patches was wrong in a way only rendering could show.** `animationDuration` sits
*inside* a `style` object on the tab panel; replacing the key with `className` produced
`style="class-name:prisme-instant"` — a style attribute that is also nonsense, and which the guard
caught immediately with its own name. Two of the five needed the surrounding object read rather than
the line replaced.

**`react-radio-group` sized its hidden input from a measurement.** `useSize(control)` fed the
button's measured width and height into the inline style, and a measurement cannot be a class. Drop
it and the input takes its default size instead — safe here because the input is
`pointer-events: none`, so the size was only ever for a click target that cannot be clicked, and the
alternative was leaving a dynamic inline style in place.

**The `images` check earned its place twice, and both findings were the kind nothing else
catches.** `patches/` was not copied into the build context, so `pnpm install --frozen-lockfile` died
with *"Failed to read patch file … No such file or directory"* — no test, no lint and no typecheck
can see that, because none of them builds a container. And once that was fixed, `pnpm deploy` on the
**API** image refused the patches as unused: `patchedDependencies` is workspace-wide, while the
deploy is one application's subgraph, and the API and sync entrypoint contain no Radix at all.
`PNPM_CONFIG_ALLOW_UNUSED_PATCHES=true` tells pnpm that is expected — not a suppression, since the
patches *are* used by the image that has the dependency, and `prisme-web` still builds with them
applied. Both images were then built locally, and the runtime assertions hold: `/healthz` 200 with an
unreachable database, `/readyz` 503, running as nonroot.

**A stale test database refused to migrate, correctly.** Running the suite after switching branches
produced eight suite failures reading *"migration 0008 (bindings) is applied in the database but not
shipped by this image — the database is ahead of the binary"*. That is the migration runner doing
exactly what `/readyz` promises, against a local database that the other branch had migrated. Worth
recording because the message is so good that it took ten seconds to diagnose, and because the same
thing in a cluster is a rollout-ordering bug rather than a local annoyance.
