**Agent:** Claude · **Duration:** one run · **PR:** [#205](https://github.com/vchatela-org/prisme/pull/205) · **Outcome:** `v0.19.0` is tagged on `44e5f53`,
both images are published and read back from GHCR, the Release is published, and the deployment
pins it. `v0.18.0` was never pinned.

## What was decided that `/release` does not decide

- **v0.18.0 was skipped, not pinned first.** Its first writing pass wanted one top-level task per
  key result of every objective under way, and the deployment's create threshold of 0 refuses that
  whole pass, anchor updates included. ADR-0038 replaced that placement before any pin, so the pin
  moved straight from 0.17.0 to 0.19.0.
- **The deployment's create threshold moved from 0 to 40** in the same deployment-repository PR,
  #1881, on the API and the sync CronJob alike. The first writing pass creates the key-result
  subtasks that have no exact-title match, and a counted upper bound was below 30. The threshold of
  0 also refused the first initiative ever created in prisme (S8), so it was not kept as a
  steady-state value either.
- **A `plan` pass was run on the live instance before the first scheduled pass**, as a one-off Job
  from the CronJob with `plan`, which writes nothing and is not held to the sync window. It reported
  2 objectives going back to draft and 6 objective tasks to give. Those are the counts the design
  predicted from the database (counts only; no title was read). The Job was deleted afterwards.
