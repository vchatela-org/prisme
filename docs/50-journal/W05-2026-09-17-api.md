# W05 · 2026-09-17 · REST API, OpenAPI, and the scope every route declares

**Agent:** w05-api · **Duration:** one session · **PR** #22 · **Outcome:** complete

## What was done

`apps/api` grew from W00's shell into the API the web UI, the MCP server and any
script will read through. 53 routes under `/api/v1`, every one declaring the
scope it requires, every one parsed at the boundary in both directions.

- **A route kit** (`http/`). A route is data — method, path, scope, schemas,
  handler — and the router, the OpenAPI document and the contract test are
  generated from that one object. `scope` is required with no default, so a
  route that forgets it does not compile.
- **The DTO layer** (`dto/`), including the ownership matrix expressed as HTTP
  refusals: the fields each write endpoint will not accept, each with the
  sentence naming who owns it instead.
- **The store** (`store/`) and **the service layer** (`services/`), which is the
  layer W06's MCP tools will call. Every rule lives there once.
- **The query surface** designed around the screens: Focus, Inbox, Backlog,
  Balance, Timeline, KPI.
- **`POST /sync`**, calling `@prisme/sync` in process behind the reconciler's
  advisory lock, defaulting to `plan`.
- **A generated OpenAPI document** at `GET /api/v1/openapi.json`, and typed
  response types exported as `@prisme/api/client`.

## Decisions taken

**The authorizer is a parameter whose default refuses everything.** W14 owns the
mechanism. W05 owns the question and the answer when nobody is installed to
answer it, which is `401` on every business route. Not a stub that says yes for
now: an instance holding read/write tokens to a whole planning workspace should
serve nothing rather than serve it to anyone.

**The contract test reads back what was mounted, not what was declared.** The
type system already demands a scope on a registry entry, so iterating the
registry would prove nothing. The failure worth catching is a route added
straight onto the Hono app — reachable, undescribed, unscoped — so the test
builds a real app, reads `app.routes`, and fails on anything reachable that the
registry does not describe. It also fails on a declared scope that no route
requires: a permission that can be granted and means nothing is how a token ends
up looking narrower than it is.

**A refused field and an unknown field get different answers.** `due` on an
initiative is neither a typo nor a field that does not exist — it is a caller
acting on a wrong belief about who writes it. `400` naming the field *and its
owner* is the only answer that corrects the belief. Unknown fields get
`unknown_field`; invalid values get `invalid_request`. All three name the field.

**The response is parsed on the way out.** What is serialized is the schema's
output, so a field the contract does not describe cannot reach a caller even if
a handler produces one — and a field the contract *does* describe that a handler
got wrong is a 500 rather than a response the OpenAPI document does not match.

**The ranking is recomputed per request, not read back.** `initiative_score` is
a history, not a cache: the active method's score depends on the balance factor,
which moves every time something is completed. A stored row answers "what did
this score when it was last written", which is right for a trend and wrong for a
list somebody is about to act on. Persisting a ranking is a deliberate act with
its own endpoint, `POST /initiatives/rescore` — the weekly review's *re-score
what changed* step — because an append-only history should record decisions, not
page views.

**`deadlineAtRisk` comes from the schedule engine.** The obvious implementation
is a day threshold, which would have duplicated a scoring method's parameter
outside `scoring/` and put two definitions of *at risk* on two screens. W02
already answers exactly this question.

**Filtering in SQL, ranking and paging in memory.** The scoring method is a
plugin, so an `ORDER BY` would mean re-implementing the active method in SQL —
two orderings of the same data, diverging the first time one changes. Sorting
the backlog by `score` sorts by **rank**, the position in the ordering the
method produced, so the list somebody reads is the list that chose their week.

**A weight is never writable through its area.** `PATCH /areas/{key}` refuses
`weightPct` by name and points at `PUT /areas/{key}/weights/{year}`. Writing one
to a Run or Signals lane is refused with `422`.

No new ADR was needed, and nothing here contradicts an accepted one.

## Surprises

**The append-only triggers refuse `DELETE`, so the test reset cannot use one.**
The first integration run failed with `event_log is append-only; DELETE is
refused` — the guard working exactly as written. The reset now `truncate`s,
which bypasses row triggers, and therefore has to run as the schema owner rather
than as the application role. That is the honest shape: the application
genuinely cannot unrecord a row, and a test must not be able to either through a
path the application has.

**The driver returns `jsonb` as text.** `factors` arrived as
`'{"costOfDelay":13}'` — a string on which every property access silently yields
`undefined`, while the row type says `Record<string, number>` and the type
checker sees nothing. Affected `initiative_score.factors`, `event_log`'s
before/after, and a review session's checklist and snapshot. Fixed with an
explicit parse in the store. Only a query against a real database could have
shown it, which is the same way W04 found its two date bugs.

**`Deps` cannot be inferred from a handler's second parameter.** TypeScript
resolves it to `unknown`, and every `services.…` in every route becomes an
error. `defineRouteFor<Services>()` binds it once so the route modules read as
declarations.

**Two literal uuids tripped the privacy deny-list**, both placeholders of mine.
Both are better without one: the cycle check's prospective id is now the
sentence it prints in an error path, and the 404 test derives its id. The
deny-list is right to watch for that shape.

## Follow-ups

- **W14** installs the authorizer. The hook is `AppDependencies.authorizer`, and
  the request it receives carries `stateChanging` so the origin check does not
  have to re-derive it. Every route already declares its scope.
- **W06** builds MCP tools over `services/` — not over the store, and not over
  the routes.
- **W08–W11** import response types from `@prisme/api/client` and add the
  dependency to `apps/web`. The generated document is at
  `GET /api/v1/openapi.json`.
- **Settings are read-only**, and there is no `PATCH /settings`. Everything that
  changes behaviour is deployment configuration; the write freeze in particular
  is lifted by a human working through the migration sequence. The sentences for
  a future write path are in `dto/ownership.ts`.
- **The adoption surface is the ledger, not the queue.** W12 owns candidate
  generation and matching; W05 serves what those decisions land in, plus whether
  each is actually bound.
- **`progressComputed` for a key result is computed from the initiatives that
  serve it**, because a key result's own anchor is bound in
  `entity_external_ref` rather than in `task_mirror.anchor_for`, which references
  an initiative. W13 should confirm this reading when it backfills.
- **OQ-2 is still open.** The work-in-progress limits and the schedule's
  concurrency are named in one place, `SERVICE_DEFAULTS`, so closing it is one
  edit.
